# Optical Collection Opportunity Analysis

OEL's public collection-opportunity workflow answers a bounded engineering
question: during one deterministic propagation, when can one declared optical
payload observe one WGS84 surface target while satisfying geometry, lighting,
pointing, first-order resolution, storage, and supplied downlink constraints?

It produces inspectable opportunity evidence. It does not claim calibrated
image quality, weather-aware availability, autonomous scheduling, or
collection authority.

## Quickstart

Run the deterministic public example:

```bash
python -m sim.collection \
  examples/collection/public_equatorial_optical_collection.json \
  --output outputs/public_equatorial_optical_collection/evidence.json
```

The command reads an `oel.collection_opportunity_problem.v1` JSON object and
writes an `oel.collection_opportunity_evidence.v1` packet. Omit `--output` to
print the packet without retaining it.

## Problem Contract

The v1 contract contains:

- one UTC epoch and one bounded deterministic ONP propagation;
- one spacecraft Cartesian ECI state;
- one zero-altitude WGS84 target;
- one rectangular, pushbroom, or axisymmetric hard-FOV optical payload;
- nadir-fixed or ideal target-track-gimbal pointing;
- range, off-nadir, incidence, Sun-elevation, spacecraft-illumination,
  gimbal-angle, slew-rate, settling, collection-duration, and effective-
  resolution limits; and
- optional storage screening plus analyst-supplied, content-identified
  downlink-window evidence.

The duration is limited to seven days and the sampled history to 200,000
points. Transition refinement must be tighter than the propagation cadence.
Unknown fields, duplicate JSON keys, wrong JSON types, fractional integer
fields, and other invalid or ambiguous inputs fail closed.

## Geometry, Time, And Pointing

The workflow reuses OEL's deterministic ONP propagation, WGS84 ray/ellipsoid
intersection, rich surface-target geometry, conical eclipse, event refinement,
and task-opportunity contracts. It records the exact normalized problem hash.

The initial v1 frame path uses a leap-second-aware UTC epoch and OEL's simple
GMST Earth rotation. Solar geometry uses OEL's bounded analytic-enhanced Sun
provider. Both choices are named in the evidence packet; neither is silently
presented as EOP- or SPICE-quality ephemeris evidence.

Target-track pointing centers the target in the declared sensor frame and
records the required gimbal angle. Required slew rate is estimated from
centered finite differences of the commanded line of sight and compared with
the declared payload limit. Settling time is removed from the beginning of
each refined raw opportunity before minimum-duration and resource screening.
This is an attitude-feasibility screen, not an actuator-torque or flexible-body
simulation.

Nadir-fixed pointing commands no gimbal angle or gimbal slew; target
off-boresight acceptance is governed by the declared hard FOV. The sensor
mounting convention is `+X` cross-track, `+Y` along-track, and `+Z` boresight,
including for asymmetric pushbroom fields.

Before transition bisection, each propagation interval is searched on a
bounded sub-cadence interior grid. The evidence packet records its actual
maximum spacing and sample count. This discovers an opportunity whose coarse
propagation endpoints are both unavailable without presenting finite sampling
as continuous proof; studies sensitive to windows narrower than the recorded
discovery cadence still require a smaller propagation step and convergence
evidence.

## Optical And Footprint Evidence

The first-order optical ledger retains these transparent equations:

```text
diffraction resolution = 1.22 * wavelength * slant range / aperture
ground sample distance = detector pitch * slant range / focal length
sampling resolution    = 2 * ground sample distance
effective resolution   = max(diffraction resolution, sampling resolution)
```

Each term is divided by the target-normal projection cosine to represent the
declared incidence geometry. These equations are useful for requirement
screening; they do not model MTF, jitter, smear, atmosphere, radiometry,
processing, or measured payload performance.

At every candidate midpoint, the declared hard-FOV boundary is intersected
with WGS84. The packet retains each boundary hit and latitude/longitude, plus
a target-centered ENU shoelace area and corner-chord width/height when the
entire boundary intersects. Those are explicit local approximations, not exact
geodesic swept-area claims.

## Storage And Downlink

Resource screening is opt-in through `resources.enabled`. When enabled, the
workflow checks whether the observation fits in declared storage and, when
requested, whether later supplied downlink windows deliver at least the
observation's generated bytes by the analysis horizon.

Every supplied downlink window requires a 64-character
`source_product_sha256`. OEL intentionally does not invent RF availability in
this workflow. Produce link windows with the directed-link analysis or another
trusted source, bind them to their source content, then supply the retained
capacity evidence here. The v1 resource screen evaluates each candidate
independently; it is not a multi-observation storage timeline or scheduler.
The v1 screen is a single downlink stream, so semantic duplicates and
overlapping supplied windows fail validation instead of having their capacity
double-counted.
When using collection evidence with the public multi-asset mission-scheduling
source adapter, disable this independent resource screen. The adapter rejects
pre-screened collection evidence so one authoritative scheduler owns storage,
downlink precedence, station contention, and delivered-data accounting.

## Evidence Packet

The output retains:

- normalized problem, its SHA-256, and model/schema versions;
- frame/time and solar-ephemeris provenance;
- every sampled availability decision and primary rejection reason;
- refined acquisition/loss transitions and censored boundaries;
- raw and settled opportunity intervals;
- range, geometry, illumination, slew, optical-quality, and footprint
  evidence;
- storage/downlink dispositions, source window identifiers, and source-product
  SHA-256 values;
- accepted public `TaskOpportunity` records; and
- explicit resource bounds and non-claims.

An accepted opportunity means the declared bounded checks passed. It does not
mean a collection was commanded, executed, successful, or legally authorized.

## Validation Basis

The public regression suite validates this slice without STK, ODTK, or another
paid service:

| Claim | Public validation |
| --- | --- |
| Diffraction, sampling, and effective resolution | Direct closed-form equation checks |
| Sensor frames and target centering | Orthonormality, handedness, and boresight-vector checks |
| Footprint intersection and dimensions | WGS84 ray intersections plus a closed-form nadir footprint case |
| Sun direction and distance | Independent ERFA `epv00` comparison at J2000 |
| Opportunity boundaries | Shared event-refinement tests and an end-to-end equatorial pass |
| Slew, lighting, and resolution gates | Negative fixtures retaining the exact rejection reason |
| Settling, storage, and downlink | Accepted and rejected end-to-end resource fixtures |
| Input integrity | Non-surface target and unbound downlink evidence rejection |

The validation establishes deterministic equation and workflow correctness
inside this contract. Calibrated sensor-performance claims require measured or
otherwise independently governed evidence for a named payload and environment.

## Local Edition And Private-Service Boundary

Public core owns the deterministic single-target geometry, transparent optical
screening, refined opportunities, bounded resource checks, evidence packet,
and small validation fixtures.

The local v1 workflow does not include weather/cloud/terrain services,
calibrated payload libraries, exact or controlled-accuracy swept coverage,
managed or rolling-horizon multi-asset scheduling, campaign-scale
storage/downlink timelines, advanced radar/radiometry, or proprietary data
connections. The separate local exact scheduler remains available for at most
18 supplied opportunities. Hosted service infrastructure and the Manifold
remain private.

## Numeric backend

`numeric_backend` defaults to `"rust"`. Use `"python"` to select the reference
arithmetic explicitly. The selected backend is retained in the normalized
problem and its semantic identity, including when `"python"` is selected. The
Rust path uses native local-nadir, target-track frame, gimbal-vector, and
analytic Sun arithmetic (wheel 0.17.0 or newer); missing required native symbols
fail before propagation. Geometry gates, quality metrics, footprint
boundaries, transition refinement, resource screening, and evidence remain
Python. Each assessment snapshots the retained state arrays once and
neighboring slew queries evaluate only their required gimbal vectors.
