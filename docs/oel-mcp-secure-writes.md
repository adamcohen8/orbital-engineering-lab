# MCP secure output writes

The local MCP adapter treats output authorization and output creation as two
separate decisions. `MCPPathPolicy` authorizes an absolute output path under an
explicit configured write root. `sim.security.output_writes` then protects the
actual bytes written after that decision.

## Shared producer contract

Engine producers may accept the small `OutputWriter` protocol:

```python
class OutputWriter(Protocol):
    path: Path
    root: Path
    logical_root: Path

    def write_bytes(
        self, relative: str | Path, payload: bytes, *,
        mode: int = 0o600, parents: bool = True,
    ) -> Path: ...

    def write_text(self, relative: str | Path, text: str, *, encoding: str = "utf-8") -> Path: ...
    def open(self, relative: str | Path, mode: str = "xb", *, permissions: int = 0o600): ...
    def mkdir(self, relative: str | Path) -> Path: ...
    def read_bytes(self, relative: str | Path, *, max_bytes: int | None = None) -> bytes: ...
    def sha256(self, relative: str | Path) -> str: ...
    def publish_file(self, relative: str | Path, source: str | Path) -> Path: ...
    def update_existing_bytes(self, relative: str | Path, payload: bytes) -> Path: ...
```

The producer receives the logical final output directory in `output_dir` and a
descriptor-bound writer for the physical writes. New files are created
exclusively with `O_EXCL|O_NOFOLLOW`; an existing entry, symlink, special file,
or traversal component is rejected. `update_existing_bytes` is reserved for a
manifest created and finalized by the same operation.

For producers that already receive logical absolute paths, the shared helper
functions `write_output_bytes`, `write_output_text`, `open_output`,
`mkdir_output`, `read_output_bytes`, `sha256_output`, and `copy_output_file`
select the context-bound writer automatically. `bind_output_writer` establishes
that context. While it is active, a path outside the writer's `logical_root`
fails closed; with no bound writer the helpers retain the ordinary CLI fallback.
`update_output_bytes` and `update_output_text` are reserved for an operation's
already-created manifest and use the writer's owned-inode check.
`list_files` and `file_record` inspect and hash evidence through the retained
directory descriptor. They reject special files and symlinks; hashes are streamed
so a large artifact does not require a second in-memory copy. The manifest
completion helper accepts this writer to keep its recorded sizes and hashes
bound to the same output directory after a visible parent-path replacement.
`staged_output_file` is the per-file escape hatch for a path-only library: it
yields a server-private physical path and publishes unchanged bytes on success.
The producer must use its logical path when constructing content-bound metadata.

The implementation is in `sim.security.output_writes`. The MCP module
`integrations.oel_mcp.secure_writes` only re-exports the shared implementation
for compatibility. Engine modules must not import the MCP integration layer.

## Path-facing producers

Producers that cannot yet accept a writer may use `staged_output()` only when
their persisted content is stage-compatible. The adapter gives the producer a
server-private 0700 temporary directory, then publishes its regular files
through the retained final directory descriptor. Publication is recursive,
exclusive, and no-follow. The complete private staging tree is checked for
unsafe entries before publication starts. Collisions and I/O failures fail the
operation; any files already created in the approved output are retained as
incomplete evidence. Failure cleanup does not unlink final output names, since
a concurrent replacement could make that delete an unrelated file. Retained
partial files still block exclusive retries; inspect the failure record and
choose a new output destination. For a content-bound single-file producer,
`staged_output_file()` avoids rewriting the generated bytes and leaves logical
path, hash, and product-ID construction to that producer.
Published files are private to the owner (`0600`), with the owner execute bit
preserved (`0700`) when the staged source is executable. Group, other, and
special permission bits are not copied.

The staging parent is selected by the server. Caller-selected staging parents
are rejected. The final directory descriptor remains anchored if a visible
output path is renamed or replaced while the producer is running.

Staging is content-compatible only when persisted paths are relative to the
output root or the producer has an explicit logical-output parameter. MCP may
rewrite paths in its response envelope after publication. It must not perform
generic recursive string replacement inside producer JSON, manifests, or
products because that can invalidate content hashes, product IDs, source
identity, and cross-file references.

## Current producer boundary

MCP handlers supply logical/physical output bindings for scenario execution,
agent-task packets, hypothesis studies, dynamics OD, Scale refresh-to-ONP,
event-centered handoffs, trajectory optimization, interchange materialization,
FSW/FSWDK authoring, and spacecraft twins. Engine helpers use the bound writer;
path-only libraries such as SQLite and media encoders use private per-file
staging. Producers construct persisted paths and content hashes using the final
logical paths before publication.

Plots and review media use private staging with completed-run artifact-index
recording disabled or separately protected. CR3BP rendering preserves existing
run indexes and records new media in its own exclusive operation receipt.
Native FSW MCP builds publish an immutable pointer within the declared output
directory, keyed by source, ABI, and profile identity. Resolution verifies the
current identity and executable hash; ordinary CLI builds retain their legacy
pointer behavior.

These bindings preserve the producer's source identity and hash relationships.
Post-hoc generic path rewriting inside artifacts is not a substitute for them.

## Platform bounds

The writer requires POSIX descriptor-relative operations, `O_DIRECTORY`,
`O_NOFOLLOW`, and the needed `dir_fd` support. macOS is the exercised target.
Linux compatibility is not a qualification claim until it is included in the
project validation matrix. Windows fails closed with
`SecureWriteUnavailable`; this document makes no Windows qualification claim.

The boundary protects against concurrent rename/symlink substitution and
pre-created collisions within the approved roots when the MCP process and its
account are trusted. It does not protect against a privileged host/root
attacker, a compromised kernel/filesystem, or code that can modify the MCP
process itself.
